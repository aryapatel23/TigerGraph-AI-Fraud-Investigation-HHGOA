## 1. `transactions.csv`

**Row count:** 590,742 data rows + 1 header = 590,743 lines
**File size:** ~708 MB
**Join key:** `TransactionID` joins to `identity.csv`
**Date range:** 2016-07-02 to 2016-12-31

Primary fact table. Every row is one card transaction. Contains all 393 original Vesta/IEEE-CIS columns plus four columns added by TigerGraph. The `isFraud` label has been **removed**; `risk_score` is the proxy signal.

### Added columns (TigerGraph)

| Column | Type | Description |
|---|---|---|
| `customer_id` | string | e.g. `C06075`. Derived from the card issuer field; one customer can have several cards. Card IDs look like `C01234-K1`. |

You may use them as signals. Say so in your evidence rather than pretending to know what V127 means."* Values are floats; many are null per row.

## 5. Fraud Policy, Patterns, and Regulatory References

### 5.1 Bank Fraud Policy Summary

The full policy is embedded in `README.md` (Fraud Policy v1.0, lines 190-286). **There is no separate policy file in the folder.**

Key principles:
- The `risk_score` is a reason to look, **never a verdict**.
- The only confirmed outcomes live in `closed_cases_history.csv`.
- The agent recommends actions; only `auto`-routed actions may be executed without human approval.
- Investigations must stop when fraud probability is >= 0.85 or <= 0.15, supported by at least two independent pieces of evidence.

**Available actions and approval routes:**

| Action | Approval Route |
|---|---|
| `ALLOW_TRANSACTION` | `auto` |
| `MONITOR_CARD` | `auto` |
| `MONITOR_CONNECTED_CARDS` | `auto` |
| `WARN_CUSTOMER` | `auto` |
| `VERIFY_WITH_CUSTOMER` | `auto` |
| `STEP_UP_AUTH` | `auto` |
| `GENERATE_REPORT` | `auto` |
| `CREATE_CASE` | `auto` |
| `ESCALATE_TO_ANALYST` | `auto` |
| `CLOSE_NO_FRAUD` | `auto` |
| `DECLINE_TRANSACTION` | `L1` (team lead) |
| `BLOCK_CARD` when exposure <= $2,500 | `L1` |
| `BLOCK_CARD` when exposure > $2,500 | `L2` (fraud manager) |
| `BLOCK_ALL_CARDS` | `L2` always |
| `FILE_REPORT` | `L2` always |

**Policy rules:**

| Rule | Summary |
|---|---|
| R1 | Verify before blocking on a weak signal. If fraud probability < 0.70 and only one signal, use VERIFY_WITH_CUSTOMER or STEP_UP_AUTH before any block. |
| R2 | Customer denies the transaction: BLOCK_CARD + CREATE_CASE. Add FILE_REPORT if exposure > $1,000 or case connects to shared device or another card's fraud. |
| R3 | Customer confirms the transaction: CLOSE_NO_FRAUD. Note confirmation in case file. |
| R4 | No reply within 24 hours: MONITOR_CARD + DECLINE_TRANSACTION for pending authorizations. Escalate if exposure > $500. |
| R5 | Card testing: three or more small online auths within an hour + larger purchase: DECLINE_TRANSACTION + STEP_UP_AUTH. If purchase over $100 already cleared: BLOCK_CARD. |
| R6 | Shared origin across cards (same device, region, or recipient email): CREATE_CASE + FILE_REPORT + MONITOR_CONNECTED_CARDS for every sharing card. |
| R7 | Disputed charge matches customer's own recurring pattern: CREATE_CASE + VERIFY_WITH_CUSTOMER + WARN_CUSTOMER. Do not block. |
| R8 | Verdict is `uncertain` and exposure > $500, or evidence conflicts: ESCALATE_TO_ANALYST. |
| R9 | Undocumented pattern with coordinated/repeated abuse across customers: CREATE_CASE + FILE_REPORT + ESCALATE_TO_ANALYST. Describe pattern in own words; do not force into known category. |
| R10 | Never BLOCK_ALL_CARDS unless at least two of the customer's cards show confirmed fraud or credentials are confirmed compromised. |

**Case vs. SAR distinction (Policy section 3a):**
- A **case** (`CREATE_CASE`) is the bank's internal record. Open one whenever fraud probability >= 0.30, whenever evidence is requested, or when a customer disputes. Cases can be closed as fraud or legitimate, and updated as evidence arrives. Must be written into the graph.
- A **SAR** (`FILE_REPORT`) is a regulatory filing sent outside the bank. File only when fraud is confirmed or strongly suspected AND at least one of: exposure > $1,000; activity connects to shared device/region/card fraud; pattern is coordinated or undocumented (R9). A report always has a case behind it. Most cases never need a report.

### 5.2 The Five Documented Fraud Patterns

These are the patterns used in `closed_cases_history.csv` and in the `pattern` field of answer files. They are **not exhaustive** — the README explicitly states some activity in the data fits none of them.

**Pattern 1 — `card_testing`** (Policy R5)
*Signature:* A stolen card number is validated before use. Three or more tiny online authorizations (often under $5) on one card within a short window (approximately one hour), followed by a larger purchase. The sequence itself is the confirmation — no other signal is required to identify the pattern. The card number was likely sold; the actor tests whether it works before a bigger buy.

**Pattern 2 — `card_not_present_fraud`** (Policy R1-R4)
*Signature:* The card number is used for online purchases without the physical card. Amounts and product codes inconsistent with the cardholder's history, typically in a burst of 2-4 transactions within 48 hours. A single unusual online purchase is ambiguous — verify first. Distinguished from Pattern 3 by the device NOT being flagged as new.

**Pattern 3 — `card_not_present_new_device`**
*Signature:* Same as Pattern 2 (online, inconsistent purchases), but the identity record marks the device as `New` for this account (id_15 = New), sometimes combined with a proxy (id_23 non-null/non-transparent). Stronger signal than Pattern 2, but still not proof — the cardholder may simply have a new phone. Requires corroboration.

**Pattern 4 — `out_of_region_use`** (Policy R2, R3)
*Signature:* Card-present (`in_person`) purchases in a billing region (addr1) the cardholder has no transaction history in, while normal activity continues at home. Key distinction: several days of purchases in one new region may be travel, not card cloning. Simultaneous activity in two different regions is the smoking gun.

**Pattern 5 — `account_takeover`**
*Signature:* Mixed-channel activity inconsistent with the cardholder's history, often with device anomalies (id_15, id_34 match flags) and behavioral inconsistencies, pointing to stolen credentials rather than just a stolen card number. Broader than CNP fraud — may involve cross-card activity, unusual login patterns, or account detail changes.

**`undocumented`**
Used in `closed_cases_history.csv` for a small number of cases analysts confirmed as fraud but could not match to any of the five patterns. README says: "Read those notes carefully." The `analyst_notes` field contains the descriptions. Finding and correctly describing a novel pattern in the exam data is **scored**.

## 6. Fraud Labels and Proxy Signals

### Is there an "Is Fraud" label?

**No.** The original IEEE-CIS `isFraud` binary label has been deliberately removed from all files in this dataset. The README states explicitly: *"the yes/no fraud label is gone."*

### What acts as the proxy signal?

There are two distinct signals serving different purposes:

| Signal | Where | What it is | How to use it |
|---|---|---|---|
| `risk_score` (float 0-1) | `transactions.csv`, `case_pack.csv` | The bank's detection model score for each transaction | A reason to look, never a verdict. Many high scores are legitimate. Some fraud scores near zero. |
| `outcome` (enum) | `closed_cases_history.csv` only | `confirmed_fraud` or `cleared` — the only ground truth in the entire dataset | The historical label; use for retrieval, pattern matching, and calibration. |

**Critical implication:** For the 20 exam cases, there is no label at all. The agent must construct its own `fraud_probability` (0-1) from graph evidence, closed cases, and the policy — not from `risk_score` directly. The README states: *"Your `fraud_probability` should reflect what you found, and may be far from it [the risk score]."*

## 7. Answer Format (Quoted Precisely from README)

> "Submit one JSON file per case, named `<case_id>.json`, for every case in `case_pack.csv`. Twenty cases, twenty files, in a folder called `cases/` in your repository."

Each answer file has three parts:

### Top-level fields

| Field | Type | Meaning |
|---|---|---|
| `case_id` | string | From `case_pack.csv` |
| `case` | object | Part 1 (below) |
| `evidence_requests` | list | Each: `type` (customer_validation / step_up_auth / analyst_info), `asked_after_step` (int), `assumed_response` (string). Empty if nothing was asked. |
| `next_best_actions` | object | Part 3 (below) |
| `sar` | object | Part 2 (below) |
| `stop_reason` | string | Why the investigation ended here |
| `tool_calls` | int | Graph and retrieval calls made for this case |
| `tokens` | int | LLM tokens consumed for this case |
| `latency_s` | number | Wall-clock seconds for this case |

### Part 1: `case` — the bank's internal investigation record

| Field | Type | Meaning |
|---|---|---|
| `status` | enum | `open` / `closed_fraud` / `closed_legitimate` / `escalated` |
| `verdict` | enum | `fraud` / `legitimate` / `uncertain` |
| `fraud_probability` | number 0-1 | How likely the flagged activity is fraud. Scored for calibration — be honest. |
| `pattern` | enum | `card_testing` / `card_not_present_fraud` / `card_not_present_new_device` / `out_of_region_use` / `account_takeover` / `undocumented` / `none` |
| `pattern_description` | string | Required when pattern = `undocumented`: 2-3 sentences on what it is, who it affects, how you found it. Otherwise `""`. |
| `affected_txn_ids` | list of strings | Every transaction believed to be part of the same fraud episode, including the flagged one. Empty if legitimate. |
| `first_suspicious_txn_id` | string or `""` | Where the fraud episode started. |
| `connected_card_ids` | list of strings | Other cards caught in the same compromise, ring, or device. |
| `connected_device_profiles` | list of strings | Device profiles (DeviceInfo + OS + browser + screen) linking this case to other cards. |
| `exposure_usd` | number | Sum of absolute amounts of `affected_txn_ids`. |
| `evidence` | list of objects | Each: `claim` (string), `source` (graph / document / customer / external), `ref` (query name, document section, or request id), `entity_ids` (list of IDs the claim rests on). |
| `similar_prior_cases` | list of strings | Closed-case IDs from `closed_cases_history.csv` retrieved and used as memory, e.g. `["CC-0141", "CC-2671"]`. |
| `summary` | string | 2-6 sentences an analyst could read. |
| `written_to_graph` | boolean | Whether the agent stored this case in TigerGraph. |
| `graph_case_id` | string or `""` | The ID of the case vertex created, if any. |

### Part 2: `sar` — suspicious activity report

> "Not every case needs one. When your agent recommends `FILE_REPORT`, include the report."

| Field | Type | Meaning |
|---|---|---|
| `file` | boolean | Whether a SAR should be filed. Must agree with whether `FILE_REPORT` appears in final actions. |
| `reason` | string | Why file, or why not. Cite the policy rule. |
| `narrative` | string | Required when `file` is true. The report itself: **who** (customer, cards, merchants, devices), **what** happened, **when** (dates), **where** (locations, channels), **how** it was carried out, **why** it is suspicious. 6-12 sentences. This is what a regulator reads. |
| `subjects` | list of strings | IDs of customers, cards, merchants, and devices named in the narrative. |
| `total_amount_usd` | number | Total of the suspicious activity. |
| `activity_dates` | list of two strings | First and last date of the activity: `["YYYY-MM-DD", "YYYY-MM-DD"]`. |

> "If `file` is false: `narrative` is `""`, `subjects` is `[]`, `total_amount_usd` is 0, `activity_dates` is `[]`."

### Part 3: `next_best_actions`

| Field | Type | Meaning |
|---|---|---|
| `initial` | list of objects | What the agent recommended **before** any requested evidence came back. Each: `action` (from the policy), `route` (auto / L1 / L2), `reason` (cite the policy rule). |
| `final` | list of objects | What the agent recommends **after** the assumed evidence responses. Same shape. If nothing was requested, `final` equals `initial`. |
| `what_changed` | string | 1-2 sentences on why `final` differs from `initial`, or `"nothing"`. |

### Key scoring rules (quoted from README)

> "IDs must be the ones in the dataset. Made-up IDs score zero."

> "For a `legitimate` verdict, `affected_txn_ids` is empty, `exposure_usd` is 0, and `sar.file` is false."
